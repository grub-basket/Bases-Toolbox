# 0.1.53

- **Undoing a view change now undoes only that change.** Previously each view operation stored a copy of the whole `.base` file, so undoing an *older* change also wiped every newer one — rename a view, duplicate another, add a third, then undo the rename, and the duplicate and the new view disappeared too.

  Each operation now records its own inverse and applies it to the base as it is *now*: a rename undoes to a rename, a duplicate or an added view is removed again, a deleted view is put back exactly as it was (all of its columns, sort, filters and layout) at its original position, and a reorder moves it back. Later changes are left alone.

- **It refuses to guess.** If the view an undo needs has been renamed or removed since, the undo is skipped and told to you rather than applied to the wrong view — and the entry stays available, so you can retry it after sorting things out. A restored view whose name has been taken in the meantime is given a suffix instead of overwriting.

- History entries created by 0.1.52 keep working; they revert the previous whole-file way.
